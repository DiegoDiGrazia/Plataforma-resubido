Cómo funciona el cliente FRANQUICIA

Documentación del comportamiento agregado al sistema de gestión de cuentas para soportar un nuevo tipo de cliente, FRANQUICIA, que puede crear sus propias cuentas y solo ve lo que le pertenece.

1. Qué es una FRANQUICIA

FRANQUICIA es un valor más del campo tipo de m_clientes (junto a ENTE, EMPRESA, CAMPAÑA, AGENCIA y GESTION). A diferencia de los demás tipos, una franquicia:

  • Puede crear nuevos clientes desde el panel de administración.
  • Cada cuenta que crea queda "linkeada" a ella como su creadora.
  • En todas las pantallas de gestión, solo ve a sí misma y a las cuentas que creó — nunca al resto de los clientes de la plataforma.
  • No puede crear otra cuenta de tipo FRANQUICIA (para evitar franquicias anidadas).
Todo lo descrito acá es lógica de frontend: filtra qué se muestra y qué se puede seleccionar. Ver la sección Limitaciones conocidas sobre por qué esto no reemplaza validación en el backend.

2. Modelo de datos

No se agregaron columnas nuevas. Todo se apoya en dos campos que ya existían en m_clientes: tipo y datosFranquicia (texto largo, se usa como JSON). datosFranquicia tiene dos formas distintas según de qué registro se trate:

En el registro de la propia franquicia

Guarda la lista de cuentas que esa franquicia fue creando:

{
  "cuentas_creadas": [
    { "id": 301, "name": "Cliente A" },
    { "id": 302, "name": "Cliente B" }
  ]
}

En cada cliente creado por una franquicia

Queda "sellado" con quién lo creó:

{
  "creado_por_franquicia": true,
  "franquicia_id": 248,
  "franquicia_nombre": "Nombre de la franquicia"
}
Dónde se escribe

Ambas escrituras pasan en AbmClientes.jsx → handleSave(), al crear un cliente estando logueado como franquicia: primero el POST /clientes incluye el datosFranquicia del hijo, y después un PATCH /clientes/{id} actualiza la lista cuentas_creadas de la propia franquicia.

3. Quién está logueado

Para saber "quién soy" en cada pantalla se usa siempre: 

const idClienteLogueado = useSelector((state) => state.formulario.usuario.id_cliente);
Importante: no se usa state.formulario.id_cliente a secas. Ese valor cambia cada vez que un editor navega o selecciona otra cuenta para gestionar (por ejemplo desde SelectorCliente.jsx), así que no representa de forma confiable "quién inició sesión". state.formulario.usuario es el objeto que devuelve el login y no se toca después, por eso es la fuente confiable.

4. Patrón de filtrado (se repite en cada pantalla)

Todas las pantallas afectadas siguen los mismos cuatro pasos:

1. obtenerClientes(TOKEN)
→
2. buscar propio registro por id_cliente
→
3. tipo === 'FRANQUICIA' ?
→
4. filtrar por [propio id, ...cuentas_creadas]
const clienteLogueado = clientes.find((c) => c.id == idClienteLogueado);
const esFranquicia = clienteLogueado?.tipo === 'FRANQUICIA';

let cuentasCreadas = [];
try {
  const datos = clienteLogueado.datosFranquicia
    ? JSON.parse(clienteLogueado.datosFranquicia)
    : null;
  cuentasCreadas = Array.isArray(datos?.cuentas_creadas) ? datos.cuentas_creadas : [];
} catch (err) {
  cuentasCreadas = [];
}

const idsPermitidos = [clienteLogueado.id, ...cuentasCreadas.map((c) => c.id)];
const visibles = todosLosItems.filter((item) =>
  idsPermitidos.some((id) => id == item.id) // o item.id_cliente, según el caso
);

La única variación entre pantallas es qué se filtra con idsPermitidos: clientes, contratos, facturas (vía su contrato), o nombres de cliente (en Distribución, que agrupa por nombre en vez de id).

5. Pantalla por pantalla

AbmClientes.jsx El listado solo muestra a sí misma y sus cuentas creadas. Al crear una cuenta nueva, además del POST /clientes normal, se sella el datosFranquicia del hijo y se actualiza la lista cuentas_creadas propia. El dropdown de TIPO oculta la opción FRANQUICIA. AbmContratos.jsx Los listados de clientes y contratos se filtran igual. Además, dentro del modal de contrato, el selector de "Cliente" se reemplaza por un campo fijo de solo lectura con el nombre de la propia franquicia — los contratos siempre son de la franquicia, nunca de una cuenta hija.
Facturas.jsx Las facturas no traen id_cliente directo, así que se arma un mapa id_contrato → id_cliente a partir de los contratos para poder filtrarlas. También se filtra el combo de "Contrato abierto" al cargar una factura nueva.
Distribucion.jsx Las notas están agrupadas por nombre de cliente (no por id), así que acá el filtro construye una lista de nombres permitidos en vez de ids.
Dashboard.jsx Header especial: "Bienvenido noticias(d) {nombre}" + "¿Qué dashboard desea ver?" seguido del SelectorCliente, sin importar el permiso Dashboard: Selector clientes (una franquicia siempre necesita poder cambiar entre sus cuentas).

6. APIs agregadas — src/components/Apis/apis.js

Se agregó el CRUD de clientes contra la API documentada (https://services.noticiasd.com), reemplazando el endpoint legacy (panel.serviciosd.com/app_obtener_clientes) en las pantallas tocadas, ya que el legacy no garantiza traer tipo ni datosFranquicia.

7. Limitaciones conocidas

  • Todo el filtrado es de frontend. Un usuario con el token de una franquicia podría, en teoría, llamar a la API directamente y pedir datos de otro cliente. Para cerrar esto de verdad hace falta que el backend valide también tipo === 'FRANQUICIA' + pertenencia, no solo el frontend.
  • Al editar un cliente ya existente en AbmClientes.jsx, los selectores de país/provincia/municipio arrancan vacíos — no hay pre-carga desde los pais_id / provincia_id / municipio_id guardados. Como el PATCH solo manda lo que cambia, el dato guardado no se pierde, pero tampoco se ve reflejado en el modal hasta que se lo vuelve a seleccionar.
  • eliminarCliente ya existe en Apis/apis.js pero todavía no está conectado a ningún botón de la UI.
